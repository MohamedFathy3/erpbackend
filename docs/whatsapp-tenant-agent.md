# WhatsApp Agent — إعداد وتشغيل مستقل لكل Tenant

## الوظائف

- إعدادات Agent منفصلة لكل شركة وحساب واتساب: تشغيل/إيقاف، اسم، معلومات الشركة، تعليمات، رسالة handoff، واختيار الأفعال المسموحة.
- ردود نصية تلقائية فقط للرسائل النصية الواردة، تتم معالجتها عبر Laravel Queue، ولا تُرسل إلا إذا كان الحساب متصلًا والمحادثة في حالة `bot_active` وداخل نافذة خدمة WhatsApp (24 ساعة).
- الأسئلة المعرفية تُجاب من معلومات الشركة التي حفظها الـtenant. النموذج الحالي هو Gemini المضبوط عبر `GEMINI_API_KEY` و`GEMINI_MODEL` في أسرار الخادم؛ لا تُدخل مفاتيح Meta/Gemini في واجهة tenant.
- البحث عن فواتير مبيعات وأوامر صيانة سيارات يعتمد على مطابقة رقم العميل مع رقم الهاتف الوارد ضمن نفس `tenant_id`. لا تُمرر سجلات tenant آخر، ولا تُستخدم سجلات soft-deleted. الفواتير لا تمثل حالة شحن؛ لا يسمح للوكيل باستنتاج حالة توصيل.
- طلبات المواعيد التي يلتقطها الوكيل تُحفظ في صندوق خاص بالـtenant وتحوّل المحادثة لموظف. الموظف يحدد وقتًا، ثم يفحص النظام وجود تعارض في تقويم Google الأساسي للشركة وينشئ الحدث الحقيقي قبل وسم الطلب مؤكدًا. يتطلب ذلك اتصال Google صالحًا بالـscope `calendar.events`.
- يستطيع الموظف متابعة المحادثات المحوّلة والرد يدويًا. الإرسال الحر يتقيد بنافذة 24 ساعة؛ خارجها يجب إرسال قالب WhatsApp معتمد.

## النشر

1. انشر تغييرات الـBackend والواجهة معًا على الفرع المستهدف.
2. خذ نسخة احتياطية، ثم شغّل ترحيلات قاعدة البيانات في البيئة المناسبة:
   ```sh
   php artisan migrate --force
   ```
3. اضبط `GEMINI_API_KEY` عبر مدير أسرار الاستضافة (لا تضفه إلى Git). استخدم اتصالًا يدعم Queue فعليًا.
4. شغّل عامل Queue دائمًا بإدارة عمليات الاستضافة، مثل Supervisor أو systemd:
   ```sh
   php artisan queue:work --queue=default --tries=2 --timeout=60
   ```
   لا تستخدم `QUEUE_CONNECTION=sync` في الإنتاج؛ إذا لم يعمل العامل ستبقى الرسائل الواردة بلا رد آلي.
5. على كل Tenant، اربط رقم WhatsApp، اربط Google Calendar من وحدة التكاملات، افتح WhatsApp → وكيل الذكاء الاصطناعي، اكتب معلومات الشركة، جرّب الأسئلة، ثم فعّل الرد الآلي. تفعيل الوكيل يتطلب رقمًا فعالًا وGemini ومعلومات شركة غير فارغة.
6. اختبر tenant تجريبيًا: FAQ موجود/غير موجود في المعرفة، طلب فاتورة، استعلام أمر صيانة، طلب موعد بوقت متاح، طلب موعد متعارض مع حدث، وطلب موظف. لا تفتحها لعملاء عامين قبل إتمام متطلبات Meta، HTTPS، Webhooks، مراجعة الخصوصية والاحتفاظ بالبيانات.

## القيود المتعمدة

- إنشاء حدث تقويم يثبت وقتًا اختاره الموظف بعد فحص التوفر؛ الوكيل لا يحجز وقتًا من تلقاء نفسه ولا يدّعي وجود موعد مؤكد قبل موافقة الموظف.
- تأكيد التقويم لا يرسل رسالة واتساب تلقائيًا. على الموظف إرسال إشعار مناسب؛ خارج نافذة 24 ساعة يلزم قالب Meta معتمد. يلزم تثبيت قالب وإعداده tenant-specific إذا أُريدت أتمتة إشعار التأكيد.
- لا توجد في النموذج الحالي بيانات شحن عامة؛ يتاح استعلام الفاتورة وأمر صيانة السيارة فقط. إضافة أنظمة شحن تتطلب نموذجًا وبيانات موثقة جديدة.
- معالجة الصور والصوت غير مفعّلة؛ لا يرد الوكيل آليًا على الرسائل غير النصية.
- يجب تنفيذ migrations واختبارات الـBackend على بيئة PHP/Composer وقاعدة بيانات متوافقة؛ لم تُنفّذ ترحيلات على الإنتاج ضمن هذه التغييرات.
